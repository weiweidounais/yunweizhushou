# 阶段 2-2 技术开发文档｜变更、审批与审计

> 配套文档：`docs/PRD/PRD.md`（V3）、《技术适配声明》、《阶段2-1技术开发文档》。
> 本文档只覆盖阶段 2-2：变更计划、审批、模拟执行、回读验证、哈希链审计、策略 allow/ask/deny；不做 20 条评测（2-3）、不做正式前端（阶段 3）。

## 一、阶段目标

- 交付范围：在只读诊断之上，打通「变更计划 → 人工审批 → 模拟执行 → 回读验证 → 审计」；所有写操作由确定性策略和审批绑定约束，不交给模型自主决定。
- 阶段产物：`change_plans` / `approvals` / `audit_log` 表；`propose_change`、`execute_change`、`verify_change` 工具；策略服务；审计哈希链；临时界面的变更卡片、批准/拒绝、审计弹层；测试；README 更新。
- 验收标准：
  - 未审批执行被拒绝，并写入审计；
  - 审批后执行成功，回读验证成功，审计链可验证；
  - 审批与计划 hash 绑定，参数被改/过期/重放均拒绝；
  - forbidden 动作直接拒绝；
  - 审计写入失败时执行中止；
  - 界面上能完成「发起变更 → 批准 → 执行 → 回读 → 看审计」。
- 明确不做：真实设备执行（模拟执行器）、双人复核、批量变更、变更窗口/冻结期完整策略（只做最小校验）、20 条评测（2-3）、正式前端（阶段 3）。
- 主链路片段：`propose_change → 用户批准 → execute_change → verify_change → audit`。

## 二、技术适配摘要

- 沿用阶段 2-1 的后端先行 + 临时验收界面；不引入新框架。
- 新增：SQLite 三张表、`ChangeService`、`AuditService`、`PolicyService`、`MockChangeProvider`、三个工具、四个 API。
- 模型仍为 DeepSeek OpenAI 兼容接口；诊断走快速模式，变更请求走普通工具循环。
- 模拟执行：不碰真实设备，执行结果明确标 `simulated=true`。

## 三、技术栈与模型

- 同阶段 2-1：Python 3.12、FastAPI、Pydantic、SQLAlchemy + SQLite、pytest、httpx。
- 模型：`deepseek-chat`（OpenAI 兼容）；变更链路的工具调用最多 4 轮，输出上限 1600 tokens。
- 不引入：Alembic、任务队列、真实 Ansible/Jumpserver、双人复核。

## 四、环境与配置

```ini
POLICY_MODE=approval          # read_only | approval | full
READ_ONLY_MODE=false          # true 时所有写操作 deny（演示默认 false）
APPROVAL_TTL_MINUTES=15
AUDIT_HASH_PREFIX=dcops
```

- `POLICY_MODE=read_only` 时 `propose_change` 直接拒绝；`approval` 时 change_low/high 需审批；`full` 仅演示用，change_low 可放行（本阶段不默认开）。
- 审批人：本地单用户 `local`，`approved_by` 记录为 `local`；V2 再接双人。
- 执行端口/服务同 2-1（8020）；不新增外部依赖。

## 六、数据、资产与状态

- `change_plans(id, session_id, owner_id, asset_id, action, params_json, reason, impact, rollback, window_start, window_end, plan_hash, status, dry_run_json, execution_json, verification_json, created_at, updated_at)`。
- `approvals(id, plan_id, plan_hash, approved_by, approved_at, expires_at, used_at, comment)`。
- `audit_log(id, ts, session_id, actor, action, target_type, target_id, params_digest, plan_hash, approval_id, result, error, prev_hash, hash)`。
- 计划状态：`pending_approval → approved → executing → succeeded → verified`；拒绝 `rejected`；失败 `failed`/`unknown`。
- 审批：15 分钟过期、一次性、plan_hash 绑定；参数变更/重放/过期都拒绝。
- 审计：每条 `hash = sha256(prev_hash + canonical_record)`；首条 prev_hash = 64 个 0；`GET /api/audit/verify` 重算。
- 归属：`owner_id=local`，查询按 owner 过滤。

## 七、API / 工具设计

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/changes/{plan_id}/approve` | 批准计划，返回 approval_id、过期时间；写审计 |
| POST | `/api/changes/{plan_id}/reject` | 拒绝计划，写审计 |
| GET | `/api/changes/{plan_id}` | 计划详情 + 审批状态 |
| GET | `/api/audit?limit=50` | 审计列表 |
| GET | `/api/audit/verify` | 重算哈希链 |

工具：
- `propose_change(asset, action, params, reason, impact, rollback, window_start?, window_end?)` → 策略检查 → 创建计划（pending_approval）→ 返回 plan_id/plan_hash/审批提示；forbidden 直接失败并审计。
- `execute_change(plan_id)` → 校验计划状态、审批存在/未用/未过期/hash 一致 → dry-run → 模拟执行 → 写审计；无审批拒绝。
- `verify_change(plan_id)` → 模拟回读指标/告警 → 计划置 verified → 写审计。
- `GET /api/chat` 响应新增 `change_plan`，UI 据此显示审批卡片。

## 八、Prompt 设计

在阶段 2-1 系统提示词基础上新增：
- 变更请求先调用 `propose_change`，向用户说明 plan_id、影响面、回滚，等待用户批准；**不得自行声称已批准**。
- 用户明确说「已批准/执行」后才调用 `execute_change(plan_id)`；执行后必须调用 `verify_change(plan_id)`。
- 输出仍要短：计划说明 ≤200 字；执行结果 ≤200 字。
- 不能绕过 `execute_change` 的审批校验；工具报错要如实转述。

## 九、验收界面

- 临时 HTML 新增：
  - 变更卡片：资产/动作/参数/理由/影响/回滚/plan_hash/状态；
  - 「批准」「拒绝」按钮；批准后自动发「已批准 plan_id=…，请执行并回读验证」；
  - 审计按钮：弹出最近 50 条审计 + 哈希链校验结果；
  - 侧栏新增「变更演示」示例。
- 仍不做正式视觉/移动端（阶段 3）。

## 十、测试要求

新增 mock 测试（至少 8 条）：
1. propose 创建 pending 计划并写审计；
2. forbidden 动作拒绝并审计；
3. 未审批 execute 拒绝；
4. 批准 → execute → verify 成功，审批 used_at 写入；
5. 审批过期拒绝；
6. plan_hash 不一致拒绝；
7. 审计写失败时执行中止；
8. 篡改审计记录后 verify 链失败；
9. API approve/reject/audit 返回结构；
10. 变更请求不被快速模式误吞（走普通工具循环）。

真实冒烟：用真实 DeepSeek 跑「发起隔离变更 → 批准 → 执行 → 回读 → 审计链校验」一条链路，写入 `docs/evidence/阶段2-2/冒烟记录.md`。

## 十二、风险与待确认项

- 执行是模拟的，不代表真实设备成功；生产接入必须换 ChangeProvider 并重新验收。
- 单用户本地审批，没有双人复核；V2 再做。
- 变更窗口/冻结期只做最小校验（本阶段未完整实现）。
- 没有 SSE；变更链路会有 2–3 次模型调用，约 10–20 秒。
- 必须由产品经理决定的问题：无。
