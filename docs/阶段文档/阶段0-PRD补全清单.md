## 必须问（本轮不超过 5 个）

### 问题 1：本次 demo 做到哪一步（范围与验收界面）→ 回答：A
- **结论**：只读诊断 + 审批后单设备变更 + 审计 + 最小 Web 验收界面；CLI 保留；不含手动巡检、定时、记忆、MCP、批量、多用户。
- 为什么重要：决定这次要交付多少东西，也决定阶段 2/3 的验收界面做到什么程度；PRD 的 V1.0 是 CLI，但工具包的合格线要求阶段 3 有正式前端。
- 选项：
  - A. 只读诊断 + 审批后单设备变更 + 审计，含最小 Web 验收界面（聊天 / 审批 / 审计三页）；CLI 保留；不含手动巡检、定时、记忆、MCP、批量、多用户。
  - B. 只做只读诊断 + CLI，最快看到效果，不做变更与审批。
  - C. 按 PRD V1.0 全量（含手动巡检、完整策略、Web），周期更长。
- 推荐：A。安全和审计是这类产品的核心价值；只读版看不到「审批后执行」这条主链路，全量版会把周期拉长。
- 不选的后果：选 B 看不到变更闭环；选 C 第一版周期明显变长，且手动巡检/完整策略会挤占核心链路的时间。

### 问题 2：演示数据与连接器怎么接 → 回答：A
- **结论**：内置模拟 fixtures + 四个 Provider 抽象接口；真实 Prometheus / Alertmanager / NetBox 后续接。
- 为什么重要：你没有提供监控/告警/CMDB 的地址和只读账号；直接接真实系统会引入网络、权限和敏感数据问题。
- 选项：
  - A. 内置模拟 fixtures（服务器/交换机/告警/指标/拓扑）+ 四个 Provider 抽象接口；真实 Prometheus / Alertmanager / NetBox 后续接。
  - B. 直接接你现有的 Prometheus / Alertmanager / CMDB（需要地址、只读账号、网络可达）。
  - C. 只做静态样例，不做 Provider 抽象（不推荐，后面接真实系统要重写）。
- 推荐：A。先把主链路和审批/审计跑通，接口留好，真实系统只换 Provider 实现。
- 不选的后果：选 B 开工前要等权限和网络；选 C 真实接入时要重写工具层。

### 问题 3：评测集与历史样本 → 回答：A
- **结论**：先用 20 条合成告警（现象 + 真实根因 + 建议处置）+ 评分表；真实样本后续替换。
- 为什么重要：PRD 的验收标准是 Top-1 ≥60%、Top-3 ≥85%、证据引用 100%、编造率 0；没有样本就无法证明，也无法在阶段 2 做真实冒烟评分。
- 选项：
  - A. 先用 20 条合成告警（现象 + 真实根因 + 建议处置）+ 评分表；真实样本后续替换。
  - B. 你提供 20–30 条真实历史告警（最好，但开工前需要整理和脱敏）。
  - C. 先不建评测集，只看演示效果（不推荐，无法验收 D2）。
- 推荐：A。合成样本可以先跑通评测流程，真实样本到了只换数据文件。
- 不选的后果：选 B 会阻塞阶段 2 开工；选 C 阶段 2 的真实冒烟没有判定依据。

### 问题 4：交付形态、登录与上线 → 回答：A
- **结论**：本地单用户、不做登录、只做到阶段 3；业务表预留 `owner` 字段。
- 为什么重要：决定是否要账号、是否要部署、是否产生云费用，也决定业务表要不要从第一张起带归属字段。
- 选项：
  - A. 本地单用户、不做登录、只做到阶段 3（本地可运行），不部署。
  - B. 本地 + 邀请码换 Cookie 会话，不部署。
  - C. 邀请码登录 + 部署腾讯云开发（阶段 4，需要实名、可能产生费用）。
- 推荐：A。当前是功能演示，本地单人用最简单；业务表仍预留 `owner` 字段，未来加登录不搬数据。
- 不选的后果：选 B/C 会增加登录、部署、费用和隐私处理的工作量；选 C 还要处理腾讯云实名和套餐。

### 问题 5：演示期模型费用上限 → 回答：A
- **结论**：演示期每月 50 元，超出即停。
- 为什么重要：PRD 要求单事件成本可控，但没有给金额；没有上限时阶段 2 的真实冒烟可能失控。
- 选项：
  - A. 演示期每月 50 元，超出即停。
  - B. 每月 100 元。
  - C. 不设上限（不建议）。
- 推荐：A。演示阶段以合成样本为主，50 元足够跑通；真实使用再按量调整。
- 不选的后果：选 C 可能在反复冒烟中产生意外费用；选 B 预算更宽但当前阶段用不到。
